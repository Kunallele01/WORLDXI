While building the §10 design system foundation, an initial pass on
`RatingBadge`/`DreamXiPrimaryButton`/`TraitChip` used gradient fills, glow
shadows, and a glossy top-highlight sweep (skeuomorphic style). The user
rejected this explicitly: badges "look like individual M&M chocolates", the
primary button "looks straight out of 2012", and press feedback felt
unresponsive (a slow spring animation only visibly caught up on a firm/held
press).

**Approved direction (locked in), in `app/src/main/java/com/dreamxi/app/`:**
- `core/ui/components/RatingBadge.kt` — flat solid rounded-square tile (like
  a FIFA OVR block), solid color fill, a crisp 1.5dp darker border for edge
  definition. No gradient fill, no blurred glow shadow, not a circle/sphere.
- `core/ui/components/DreamXiButtons.kt` — a "pressable block" pattern: a
  flat solid face sitting above a flat solid darker "shadow" block of the
  same shape; on press the face animates down (fast 90ms tween, not a slow
  spring) to sit flush with the block, then springs back up on release. No
  gradients, no glossy overlay anywhere on a button.
- `core/ui/components/TraitChip.kt` — flat solid fill, a clearly-visible
  (not timid) tinted border, small leading accent dot.
- The continuous grey→yellow→green→gold rating color math
  (`colorForRating` in `ui/theme/Color.kt`) was NOT the complaint and stays
  as designed — only the glossy/spherical *rendering* was rejected.

**Why this matters:** if asked to add more components (player cards, pitch
view, etc.) or to "polish"/"add depth" to existing ones, do not reach for
gradients, drop-shadow glows, or glossy highlight overlays as the default
way to add visual interest — that reads as dated 2012-era skeuomorphism to
this user. Prefer flat solid colors, crisp borders, and offset "hard shadow"
blocks for tactile/pressable feedback. Fast, snappy animations (under
~100ms) for press feedback; slow springs read as "unresponsive." See
[[dream-xi-architecture-decisions]].

**THE APP IS CALLED "ERA XI" (chosen 2026-09-01).** "Dream XI" was dropped
because Dream11 is a real and disreputable Indian fantasy app. The name states
the mechanic — an eleven assembled across eras — and the tagline is
"ELEVEN PLAYERS · EVERY ERA".

Only the DISPLAY name changed (`res/values/strings.xml`). The `applicationId` is
still `com.dreamxi.app`, and package and class names (`DreamXiApplication`,
`Theme.DreamXI`, `DreamXiButtons`, the whole `com.dreamxi.app` tree) are
unchanged — renaming the applicationId makes it a different app to Android and
forces a fresh install. Rename it properly before any store release.

**Launcher icon**: a gold football on the app's own near-black. Adaptive icon in
`drawable/ic_launcher_background.xml` and `ic_launcher_foreground.xml`, plus real
raster fallbacks for API 24-25 rendered by a throwaway PIL script into every
mipmap bucket — the stock Android Studio robot was still shipping there.
Deliberately only the central pentagon and its seams: full 32-panel detail turns
to mud at 48dp, which is the size it is actually seen at.

**Opening animation** — FIVE variants, chosen at random per launch, in
`feature/splash/SplashScreen.kt`. Four are drawn live on a Compose Canvas and
run 2.0s; the fifth is illustrated artwork and runs 3.4s, because a drawn intro
is legible the instant it resolves while a painted one has depth to take in and
was gone before it registered. Duration is therefore per-variant, not shared.

- **Strike** (kinetic): ball on a bezier into a net whose strands are polylines,
  so the bulge varies along their length rather than the net sliding as a whole.
- **Line-up** (structural): eleven dots rise into a 4-3-3, staggered, each
  overshooting slightly — anything landing exactly on its mark looks mechanical.
  The one that actually shows what the app IS.
- **Eras** (typographic): three cells roll through seasons and settle on three
  different years. Only REAL seasons appear (2019/20-2023/24); flashing 1970
  would advertise players the database does not have.
- **Floodlights** (atmospheric): banks snap on in sequence — never fade, because
  floodlights do not fade.
- **Stadium** (artwork): two painted frames cross-faded so the lights come on,
  over a slow push-in. ~308 KB. Generated by `tools/generate_intro_art.py`,
  which is re-runnable and documented; the Compose side does not care where the
  pixels came from, so real artwork could replace it by swapping two files.

The art needed several passes and the lessons are in that script: an even
speckle reads as sensor noise rather than a crowd (needs tiers and aisles), a
pitch without side stands floats in a void like a carpet, stepping a slope in 70
rectangles leaves a staircased edge, four identical haloes read as a diagram,
and a far stand as sharp as the near touchline is the clearest tell that a frame
was generated rather than observed — hence distance haze.

**Superseded — the original single animation**: `feature/splash/SplashScreen.kt`, a 2-second Compose
Canvas — goal frame, a net that ripples where the ball hits it, a ball on a
bezier with a fading trail, then the title. THREE VARIANTS chosen at random per
launch (top corner, low drive, chip). No image assets at all: a few KB, an exact
palette match, and it scales to any screen. It is the nav start destination and
pops itself off the back stack so Back can never return to it. It waits on
nothing — no ViewModel, no repository — so it can never delay a cold start.
